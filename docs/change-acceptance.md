# Change acceptance protocol, version 2

Clouseau answers two questions independently: does this implementation belong in
the repository, and is there a demonstrated reason it cannot merge? Passing
tests is mandatory evidence; it does not answer either question by itself.

The protected base supplies repository purpose, requirements, configuration and
policy. Every changed file is accounted for. The complete original and proposed
text, linked tickets, recent file precedent and actual verification receipt are
bound to immutable revisions. Fork source is read from the fork at its exact SHA.
Contributor text, source and model output are data, never executable instructions.
Each stored source citation and changed-source anchor is limited to 40 inclusive
lines. The controller partitions a longer valid model-selected interval into
entries within that limit and expands every reference to include all its parts.
Every cited line and judgment is preserved; no model retry is needed for chunking.
Unknown sources, invalid coordinates and unmatched references still stop review.
The supplied syntax includes direct source references for every changed file.
File accounting cites the corresponding changed source. An investigator may
observe the lack of a binding requirement without inventing contract authority.
That factual phase produces no approval score. Every positive binding grade still
requires trusted contract proof during final validation and at the write gate.

## Product acceptance

Inspect each material capability and mechanism. A necessary fix cannot hide an
unnecessary framework, dependency or unrelated feature. Helpers and tests inherit
justification only through the accepted outcome they demonstrably support.
Routine companion documentation of that same behavior is accounted for within
the accepted outcome. It is not a separate feature needing an explicit request
for prose. New promises, unrelated documentation and material engineering choices
still receive their own scope, factual and proportionality assessment.

| Index | Inputs and calculation |
|---|---|
| Fit, F | 35 outcome + 25 workflow + 20 domain + 10 component boundary + 10 operating model |
| Need, N | 100 × max(binding obligation, evidence × (.50 value + .30 unmetness + .20 timeliness)) |
| Proportionality, P | 100 × (1 − greatest demonstrated excess) |
| Acceptance, J | min(F, N, P), requiring at least 80 for every material unit |

Excess covers abstraction, added surface, duplicated authority, dependencies,
collateral changes and generalization beyond the demonstrated need. Every excess
claim needs a concrete narrower alternative preserving the same guarantees.
Preference, changed-line counts and helper counts alone establish no excess.
If a possible excess lacks its narrower alternative, review remains incomplete
and cannot approve. An independent integrity veto still blocks; an incomplete
repair detail cannot erase established evidence of fabricated tests.
A binding obligation must cite the trusted contract, never a contributor's claim.

## Technical findings

A finding identifies a changed or newly activated cause, feasible trigger,
affected obligation, consequence and literal evidence at its changed path.
Pre-existing debt, keywords and hypothetical vulnerabilities do not establish
a new defect. Each finding is scored separately; other good work cannot dilute it.

| Factor | Meaning |
|---|---|
| Necessity | Intrinsic obligation to correct the demonstrated defect |
| Confidence | Strength of causal evidence, rather than model self-confidence |
| Severity | Immediate consequence when the trigger occurs |
| Activation | Evidence that the trigger is feasible in the supported workflow |
| Irreversibility | Lasting damage or difficulty restoring the prior state |
| Reach | Directly affected users, data or operations |
| Detection | Difficulty discovering the failure before harm |
| Propagation | Spread into downstream obligations or systems |
| Recurrence | Repeated exposure after the first occurrence |

```
K = 1 + .25 irreversibility + .20 reach + .20 detection
      + .20 propagation + .15 recurrence
Q = 100 confidence × min(1, max(necessity, activation × severity × K))
```

Q at or above 70 blocks. Do not count the same consequence repeatedly. Partial
causal proof retains a possible confidence upper bound of 1; weak evidence cannot
discount a potentially blocking concern into approval. A confidence upper bound
of 0 requires counterevidence disproving the concern.

## Models collect facts; code owns the decision

The examiner and independent challenger receive the immutable source without the
other role's current findings, grades or verdict. They provide observations and
literal citations, not arithmetic or permission decisions. The selected atomic
grader assigns descriptive semantic levels. Code converts those levels to values
and computes every formula and threshold. All factors remain visible in the PR
ledger, including their citations and explanations.

`acceptance.grader: deepseek` uses the DeepSeek atomic grader. `typesafe` selects
the explicit Jev/DeepSeek route: Jev 1.13 handles bounded classification packets;
unresolved distributions go to DeepSeek with the same facts and no Jev answer.
A decisive negative Jev grade is never resampled with another model. Rounded
probabilities are preserved; they are not normalized into greater confidence.
Vendor confidence is never a substitute for source proof.

Failure diagnostics retain the observed immutable snapshots, investigator replies,
atomic grading packets and parsed responses, and graded reports before final
validation. These inputs support offline reproduction without calling a model
again; they do not replace fresh verification or authorize a merge.

Both routes are compared on the same investigations. Token usage includes the
investigations, grading, uncertainty routing and transport truncation attempts.
Cost estimates identify the price date and both DeepSeek tariffs. Missing usage
is unknown cost. A cheaper headline token price does not qualify a route. The
live evaluation must establish useful approvals, blocked drift and excess,
detected fabricated tests and rejected false allegations before adoption.
These policy indices are not probabilities that a change is correct.

## Gates, investigation and history

All tests and exact nonempty 100% line and branch coverage are required. The
review checks test integrity, security/isolation, compatibility/recovery,
scope/authority and completeness. Constant assertions, fake coverage, swallowed
failures and replacing the production behavior under test block approval.
Missing verification is an evidence gap rather than proof of deception. Ordinary
mocks at real dependency boundaries remain legitimate.

Unknown conditions retain ranges. A range crossing a policy threshold requires
investigation. The source reader accepts at most eight paths per request, two
additional source rounds per inspection and two complete examination cycles.
New source invalidates earlier incomplete context. A role revisits its own draft
without seeing the other role's findings; an earlier causal concern must be
retained or explicitly resolved with current-source counterevidence. Exhaustion,
malformed output, inaccessible source and provider failure hold approval. They
do not become an owner code-review request or silently switch providers.

One bot ledger is updated in place. Product rejections and technical findings
survive revision changes, renaming and disappearance from a later report.
Both roles must provide explicit evidence to close a prior blocker. Optional
observations close without creating recurring follow-up work.

## Repair boundaries and optional improvements

A verified, blocking result can propose a correction within the original changed
source paths. It must preserve the accepted outcome. The model returns complete
file contents as data; a separate author job validates hashes, paths, operations,
file modes, current PR identity and the two-attempt budget. Existing files cannot
be deleted; only a file added by this PR can be removed. No source or generated
command executes in this author job. Review controls cannot repair themselves.

The write credential must represent an author independent of the approval bot.
It creates a new commit on the internal PR branch without force. A bot reservation
records the attempt before the push, including uncertain network outcomes.
Fresh CI, source review, grading and native approval are mandatory afterward.
Fork PRs can receive normal automated assessment and merge, but their branches
cannot be written with the base repository's repair credential. Their complete
proposal remains an artifact for the contributor. GitHub may require a maintainer
to authorize a first-time contributor's secret-free workflow run.

Blast radius describes extra semantic obligations introduced by a proposed
correction. It never discounts an existing defect. xG is earned only when a
useful correction is mechanical, verified and inside the accepted envelope:

```
optional priority = min(100, Q + 20 xG / blast_radius²)
```

It creates no merge veto, new scope or approval authority. Declining an optional
opportunity ends it without repeated comments or escalation.

## Owner decisions and protected merge

Only real purpose, authority or outcome tradeoffs go to the configured owner.
Protected reviewer/control installation requires exact-revision confirmation.
The existing `/approve-intent FULL_HEAD_SHA` confirms only such a decision. It
cannot waive tests, coverage, integrity failures, technical repairs or incomplete
evidence. Ordinary coverage improvements do not require a new product decision.

Clouseau's own reviewer upgrades have a separate owner-authorized installation
route so a defective installed reviewer cannot prevent installing its verified
replacement. First qualify the frozen candidate and confirm its exact PR head.
The owner then publishes that commit to `policy-install/pr-NUMBER`:

```sh
git push origin FULL_HEAD_SHA:refs/heads/policy-install/pr-NUMBER
```

Before loading the candidate controller, a read-only guard requires the owner
actor, owner-authored open non-draft PR, the same repository, `main` as its base,
an exact matching head SHA and the owner's exact-revision intent comment.
The separate read-only AI assessment and write gate use that frozen revision.
They retain the full scored protocol, fresh PR verification, exact coverage,
evidence/history checks, native approval and existing branch protection. Failed
preparation or assessment fails the required approval job. Ordinary PR events
always load the controller from protected `main`; fork PRs cannot use this route.
Deleting an installation branch starts no installation or approval work.

The read-only assessment uploads its full source-bound record and emits a compact
digest. The separate approval job downloads that run's artifact, checks the
digest, recomputes scores, reconciles history and rechecks current CI/head/base.
It then enforces effective protection, fresh approval and enabled native
auto-merge. No provider key enters the approval or repair writer. The author
token enters only the repair writer. Same-revision intent comments reassess
metadata without rebuilding the application container.

Consumers pin a reviewed full Clouseau commit. Both required native checks must
come from GitHub Actions; main requires strict up-to-date checks, stale-review
dismissal, last-push approval, no deletion, no force pushes and no bypass actors.
The installing administrator verifies those settings; routine tokens do not
receive repository administration permission.

Merge, deployment, live health and post-deployment wiki publication remain
separate results. This protocol preserves their existing handoff and never
declares delivery merely because a PR merged.

The inspector selects source IDs and line ranges. The controller supplies their
literal text, derives unit paths from complete file accounting, and derives every
technical finding's path from a concrete changed-source anchor. Atomic defect
grading always receives that causal anchor together with the factor's citations.
These fields cannot be invented independently by a model.

Use the `evaluate-acceptance` action operation with both provider keys for the
read-only six-case qualification, including multi-file maintenance with executed
tests and corresponding documentation. Its complete artifact is written to
`work/acceptance-evaluation.json` in the caller's workspace; upload it with an
`always()` step. Passing synthetic cases is qualification evidence, not proof of
a genuine unattended merge or automatic repair.

A purpose handoff must accompany a capability whose upper fit is below 80.
An inspector's request to authorize an internal framework cannot itself make
that framework a product direction; unnecessary machinery remains repair work.
Technical necessity and severity are graded for distinct runtime, data, security,
compatibility, or verification consequences. Product scope and proportionality
are still enforced by the independent product scores and scope gate.
